# EKS managed add-on: lifecycle contract

Present contract under ADR-0003 S1, recorded before the resource moves.
It describes the code as it stands, so it claims no conformance; the gaps below are observed behaviour, not targets.
The resource-specific target is proposed requirement Q-146 and the recorded conflict is C-82 (`docs/specs/requirements/managed-services.md` in the mulga repo); both are open proposals pending review, not accepted decisions, and this record does not close either.
Paths are relative to `spinifex/` unless they start with `tests/` or `scripts/`, which are relative to the spinifex repo root.

## Scope

An add-on has an asynchronous realization: the control-plane VM renders a baked bundle into the K3s auto-deploy directory and reports delivery back.
The host side owns a desired descriptor (the record plus a staged manifest sub-key); the guest side (`scripts/images/eks-node/mulga-eks-addon-sync.sh`) pulls staged manifests through the gateway and publishes per-add-on delivery reports, which the cluster reconciler folds back into the record.
There is no generation, so the record mixes desired fields with the latest observation.

## Gaps

1. Create is get-then-put (`domains/eks/addon/owner.go` `Owner.Create`), so concurrent creates of one add-on both succeed and the later write wins; internal NATS redelivery of a create returns `ResourceInUseException`.
2. No client-token support: `clientRequestToken` is dropped on create and update, so an SDK retry of a successful create fails instead of returning the add-on as AWS does.
3. Delivery reports ignore their supplied `version` (and `ts`), so a stale or mismatched report settles the current desired state; there is no generation or incarnation fence.
4. `UpdateAddon` returns `Successful` while the add-on remains `UPDATING`, and the update `id` is the add-on ARN. AWS returns an in-progress update with its own id, tracked through `DescribeUpdate`; not verified against live AWS.
5. `DELETING` exists only in the delete response; the record and manifest are erased before any guest removal, so `DescribeAddon` returns not found immediately.
6. No observed deletion acknowledgement: the agent removes objects with `--wait=false` and reports nothing.
7. `configurationValues` is stored, staged and transported but discarded by the agent; `resolveConflicts`, `preserve` and `podIdentityAssociations` are accepted and never used.
8. Fixed: `serviceAccountRoleArn` now requires `iam:PassRole` on `CreateAddon` and `UpdateAddon`, matching `CreateCluster`/`CreateNodegroup` (`gateway/eks/passrole.go`).
9. AWS `UPDATE_FAILED` and `DELETE_FAILED` are not represented: a failed update becomes `CREATE_FAILED` and a failed delete leaves the prior status.
10. The add-on ARN lacks the per-incarnation suffix AWS appends, so a recreated add-on reuses its predecessor's ARN. This is a compatibility gap; extraction must keep the current ARN.
11. The guest/controller wire shape is duplicated and unversioned: `Manifest` in the add-on owner, `StagedAddonManifest` and `internalAddonsOutput` in the handler and gateway, `stagedAddon` in `agents/eks/gatewayfetch`, `AddonStatusReport` in `handlers/eks/state_report.go` and a `printf` in the shell agent. The HTTP body uses Go field names because the REST-JSON marshaller ignores the `json` tags, and the agent decodes it only through case-insensitive matching.
12. Reports travel over core NATS to a lease-held subscription, so they are lost whenever no reconciler runs for the cluster; delivery relies on the agent re-sending every tick.
13. The record mixes desired fields with the latest observation (`status`, `health`), and `ready` lifts `CREATE_FAILED` back to `ACTIVE`.
14. GPU auto-staging crosses from the node group into the add-on through `Owner.EnsureGPUDevicePlugin`, swallows every error, and is never undone.
15. `ListAddons` ignores `maxResults` and `nextToken`; tag actions on add-on ARNs return `NotImplemented`.
16. No ADR-0003 S5 failure or recovery evidence.
